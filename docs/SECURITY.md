# SECURITY.md — قواعد الأمان والامتثال

## المطبق فعليًا في الكود

### عزل المستأجرين (RLS)
- RLS مفعّل على كل جدول فيه `tenant_id` (migration 00002)
- سياسة منفصلة لكل عملية SELECT/INSERT/UPDATE/DELETE
- سياسات `TO anon` محدودة النطاق: قراءة المنتجات النشطة فقط + إنشاء طلبات فقط
- **لا يثق التطبيق بـ UI** — الحماية الحقيقية في قاعدة البيانات

### المفاتيح والأسرار
- `.env*` في `.gitignore` — لا أسرار في المستودع أبدًا
- `service_role` للخادم فقط (فحص الصحة + العمليات الإدارية المستقبلية)
- `anon` key للعميل — آمن لأن RLS يقيد صلاحياته
- `CREDENTIALS_ENCRYPTION_KEY` لتشفير بيانات اعتماد التوصيل (AES-256-GCM)

### التحقق من المدخلات
- Zod على كل Server Action (auth.ts)
- رقم الهاتف العراقي: regex صارم `7[5789]\d{8}` + normalization إلى +964
- كلمات المرور: 8+ أحرف مع حرف ورقم

### حماية المسارات
- Middleware يوجه غير المصادقين إلى /login
- الصفحات تحمي نفسها أيضًا (دفاع متعدد الطبقات)
- API الصحة لا يكشف معلومات حساسة

## إعدادات Supabase الموصى بها للإنتاج

1. **Network Restrictions:** قصر الوصول على نطاقات Vercel
2. **MFA** لحساب مالك مشروع Supabase
3. **Rate limiting** على Auth (متوفر في خطة Pro)
4. **Custom Access Token Hook** لحقن tenant_id في JWT

## قواعد مستقبلية (مع نمو المنصة)

- Rate limiting على API العامة (checkout, webhooks)
- سجل تدقيق يُفعَّل على كل عمليات الدفع
- نسخ احتياطي PITR (خطة Supabase Pro)
- Sentry لرصد الأخطاء
- الامتثال GDPR إن استُهدف الاتحاد الأوروبي

## قواعد المطورين

1. **لا تضع أسرارًا في الكود** — دائمًا `process.env`
2. **لا تعطل RLS** — حتى للتصحيح
3. **تحقق من كل مدخل** — Zod قبل أي كتابة لقاعدة البيانات
4. **استخدم `createClient()`** المعرفة مسبقًا — لا تنشئ عملاء ببيانات عشوائية
